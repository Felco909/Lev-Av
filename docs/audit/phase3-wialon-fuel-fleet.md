## 🔴 CRITICAL

### TMS-AUDIT-0021 — Wialon "нет данных за период" тихо записывается как настоящий ноль, затирая ранее верные цифры
**Раздел:** Wialon / Топливо
**Функция:** `getOfficialTripReport()` → `calculateVehicleTripTotals()`
**Проблема:** Когда Wialon отвечает успешно, но без таблицы `unit_generic` (юнит не передавал данных за интервал — офлайн/потеря GPS/отказ датчика), `getOfficialTripReport` (`lib/wialon/client.ts:569-578`) возвращает **успешный** результат со всеми числовыми полями = `0`, помечая ситуацию только в непрочитываемом `raw.noData`. `calculateVehicleTripTotals` (`lib/wialon/calculateTripFuel.ts:70-84`) это не проверяет, ставит `success = true` и **безусловно перезаписывает** `calculatedKm`/`calculatedFuelConsumedL` нулями — включая случай, когда до этого там уже было корректное значение из прошлой успешной синхронизации. Это прямо противоречит собственному комментарию файла ("если отчёт недоступен — 'не рассчитано', а не оценка") и `docs/fuel-data-migration.md` ("без фолбэков, показывать «—», не оценку").
**Как воспроизвести:** Закрыть/отредактировать `VehicleTrip` за интервал, где юнит не передавал данных (либо просто `departureDate === returnDate` — эндпоинт закрытия это пропускает, `close/route.ts:45-47`). Карточка рейса покажет "Пробег: 0 км" / "Расход топлива: 0 л" без единого предупреждения (UI алертит только на `success === false`, чего здесь не происходит).
**Файл/API:** `lib/wialon/client.ts:569-578`, `lib/wialon/calculateTripFuel.ts:70-84,113-131`
**Причина:** Нет проверки `raw.noData` перед записью в БД.
**Рекомендация:** При `raw.noData === true` не перезаписывать `calculatedKm`/`calculatedFuelConsumedL` (как это уже сделано для случая полной недоступности Wialon API — тот кейс обработан правильно, см. раздел "Работает корректно"), помечать `fuelCalcSource: 'no_data'` и показывать "—" в UI.

### TMS-AUDIT-0022 — `Vehicle.currentMileage` пишут 5 независимых источников без согласования; ежедневная синхронизация Wialon может двигать пробег назад
**Раздел:** Собственный транспорт / ТО
**Проблема:** Поле `Vehicle.currentMileage` пишется: (1) ручная запись топлива — только если больше текущего; (2) сервисная запись — только если больше; (3) закрытие рейса — только если больше; (4) ежедневная задача `lib/wialon/syncMileage.ts:56-74` (06:00) — **безусловно перезаписывает** значением из Wialon, без проверки монотонности; (5) `PUT /api/vehicles/[id]` — админ может вписать любое значение, включая меньшее, без валидации. Если Wialon хоть раз отдаст меньшее значение (переустановка датчика на другую машину, сброс счётчика, ручная правка в веб-консоли Wialon), суточная задача откатит `currentMileage` назад, разрушив то, что установили пункты 1-3.
**Как воспроизвести:** Смотреть код — `lib/wialon/syncMileage.ts:56-74`, нет `if (newMileage > vehicle.currentMileage)`.
**Ожидаемый результат:** Пробег машины монотонно растёт (или явно требует подтверждения при уменьшении).
**Фактический результат:** Пробег может уменьшиться незаметно для пользователя.
**Файл/API:** `lib/wialon/syncMileage.ts:56-74`, `app/api/vehicles/[id]/route.ts:33`
**Причина:** Синхронизация Wialon добавлена без учёта конвенции "только увеличение", которой следуют остальные 3 писателя.
**Рекомендация:** Добавить ту же проверку монотонности (или явный "с подтверждением" путь для отката). **Важно:** это напрямую влияет на безопасность — `lib/maintenance/calculateStatus.ts:69-70` считает `remainingKm = nextMileage - currentMileage` от этого же поля; откат пробега назад может **скрыть реально просроченное ТО** (`app/api/maintenance/status/route.ts` покажет "ок" вместо "просрочено").

### TMS-AUDIT-0023 — Прибыль по собственному транспорту нигде не учитывает расходы на ТО/запчасти — системное завышение
**Раздел:** Финансы / Собственный транспорт
**Функция:** `computeVehicleTripExpensesAmd()` — единая формула "расходов" для Dashboard, `/reports/own-fleet`, `/vehicle-analytics`, `/vehicles/[id]/economics`
**Проблема:** Формула (`lib/vehicle-trips/close-trip.ts:187-194`) суммирует `salaryAmd + perDiem + otherExpensesAmd + fuelCostAmd + FleetExpense`, но **никогда** не включает `Maintenance`, `ServiceRecord`, `PartPurchase` — эти реальные расходы видны только в отдельном отчёте `/reports/vehicle-expenses`, у которого нет ни выручки, ни прибыли. Это не расхождение расчётов между отчётами (формула везде одинаковая), а системная дыра в самой формуле: **каждая цифра "Прибыль" по собственному транспорту, показываемая пользователю где-либо в системе, завышена на полную сумму расходов на ТО/запчасти** за период/машину.
**Как воспроизвести:** Сравнить `profit` машины на Dashboard/`/vehicle-analytics` с суммой `Maintenance.cost + ServiceRecord.cost + PartPurchase.totalAmount` за тот же период из `/reports/vehicle-expenses` — прибыль везде показана без вычета этой суммы.
**Файл/API:** `lib/vehicle-trips/close-trip.ts:187-194`
**Причина:** `computeVehicleTripExpensesAmd` спроектирована вокруг `FleetExpense`/`VehicleTrip`-полей, ТО/запчасти в неё структурно не заведены (нет связи между моделями).
**Рекомендация:** Решить осознанно — либо включить ТО/запчасти (по машине и периоду) в формулу расходов, либо явно обозначить в UI, что показанная "Прибыль" не учитывает эксплуатационные расходы на обслуживание. Это финансово значимое решение — не менять формулу без подтверждения владельца (см. правило CLAUDE.md про финансовый модуль).

## 🟠 HIGH

### TMS-AUDIT-0024 — `fuelCostAmd = null` (не заполнено) неотличимо от `= 0` (подтверждённый ноль) — завышает прибыль
**Раздел:** Финансы / Топливо
**Проблема:** `VehicleTrip.fuelCostAmd` — это **ручное** поле (не из Wialon — из Wialon приходят только литры/км, стоимость топлива диспетчер вводит вручную), легко забыть заполнить. Все потребители (`computeVehicleTripExpensesAmd` и аналоги) используют паттерн `Number(vt.fuelCostAmd) || 0`, то есть незаполненное поле и подтверждённый нулевой расход считаются одинаково. Рейс с реальным расходом топлива, но незаполненным полем стоимости, тихо даёт `0` в `totalExpenses`, завышая прибыль и занижая `costPerKm`. Нигде в UI нет индикатора "стоимость не указана" в отличие от "указан 0".
**Файл/API:** `lib/vehicle-trips/close-trip.ts:191` и все read-потребители
**Рекомендация:** Различать `null` (не заполнено — не считать в expenses, но подсвечивать в UI как незаполненное) и `0` (заполнено нулём).

### TMS-AUDIT-0025 — "Пересчитать по Wialon" на закрытом рейсе — без роли, без проверки статуса, без подтверждения, без записи в историю
**Раздел:** Wialon / Права доступа / Аудит изменений
**Проблема:** `POST /api/vehicle-trips/[id]/recalculate-fuel` проверяет только наличие сессии (в отличие от `/config`/`/sync-vehicles`/`/sync-mileage`, которые корректно ограничены `WIALON_CONFIG_ROLES`). Не проверяет статус рейса. Кнопка на фронте — без диалога подтверждения. В сочетании с TMS-AUDIT-0021 это реалистичный путь тихо испортить исторические цифры уже закрытого рейса, чьи данные могли уже попасть в зарплату водителя/отчёт клиенту. Список отслеживаемых полей при правке закрытого рейса (`logClosedTripEdits`, `app/api/vehicle-trips/route.ts:367-392`) не включает `calculatedKm`/`calculatedFuelConsumedL`/`wialon*` — даже легитимный пересчёт не оставляет следа "было/стало".
**Файл/API:** `app/api/vehicle-trips/[id]/recalculate-fuel/route.ts:12-24`
**Рекомендация:** Добавить `assertRole`, подтверждение в UI для закрытых рейсов, добавить `calculatedKm`/`calculatedFuelConsumedL` в список логируемых полей.

### TMS-AUDIT-0026 — Разные отчёты по топливу/машинам расходятся по периоду, включению архивных машин и методике расчёта
**Раздел:** Отчёты / Топливо
**Проблема:** Прямое попадание в пункт ТЗ "сравнить расчёт топлива между всеми отчётами". При одинаковых исходных полях (`calculatedFuelConsumedL`/`fuelCostAmd`) 5 разных мест показывают несопоставимые числа:
- **Период:** `/reports/own-fleet`, `/reports/vehicle-expenses`, Excel-экспорт — период-фильтр по `departureDate`; `/vehicle-analytics` и `/vehicles/[id]/economics` — **за всё время**, без фильтра периода вообще.
- **Архивные машины:** `own-fleet` и Excel включают архивные машины всегда; `vehicle-analytics` и `vehicle-expenses` по умолчанию исключают.
- **Методика "л/100км":** `own-fleet`/`vehicle-analytics`/`economics` считают агрегатно `ΣЛитры/Σкм×100`; Excel-экспорт использует Wialon-овское среднее по рейсу (`wialonAvgFuelConsumptionPer100Km`) — эти числа не сопоставимы построчно.
- **`vehicle-expenses` "total"** — это `топливо+ТО+сервис+запчасти` (без `salary`/`perDiem`/`FleetExpense`), а "expenses" в формуле прибыли (`computeVehicleTripExpensesAmd`) — наоборот, без ТО/запчастей (см. TMS-AUDIT-0023). Одинаково названные "расходы" на двух страницах — разные числа по разным причинам.
Ни одна из страниц не подписывает явно свой охват (период/архив/методику), поэтому расхождение выглядит как баг для пользователя, сверяющего цифры.
**Файл/API:** `app/api/reports/own-fleet/route.ts`, `app/api/vehicle-analytics/route.ts`, `app/api/vehicles/[id]/economics/route.ts`, `app/api/reports/vehicle-expenses/route.ts`, `app/api/reports/trips/xlsx/route.ts`
**Рекомендация:** Синхронизировать хотя бы охват периода/архивных машин между `vehicle-analytics`/`economics` и остальными, либо явно подписать в UI "показатель за всё время" / "включая архивные".

### TMS-AUDIT-0028 — Закрытый рейс собственного транспорта не заморожен; прибыль может незаметно измениться неделями позже
**Раздел:** Собственный транспорт / Финансы
**Проблема:** Закрытие `VehicleTrip` намеренно (согласно комментарию в коде) ничего не блокирует — выручка/расходы всегда пересчитываются live по текущим привязанным заявкам. Привязку/отвязку заявки можно сделать независимо от статуса рейса. Сам факт смены привязки логируется, но нет записи "это изменило ранее показанный итог с X на Y" — по сути то же явление, что TMS-AUDIT-0016 (фаза 2) для заявок, только на уровне рейса.
**Файл/API:** `app/api/vehicle-trips/[id]/close/route.ts:20-23`, `lib/vehicle-trips/attach-service.ts:10-13`
**Рекомендация:** Решение продукта — либо сознательно принять (текущая логика), либо ввести подтверждение/лог при перепривязке заявок к уже закрытому рейсу.

### TMS-AUDIT-0029 — Истекающие документы архивной машины продолжают показываться на Dashboard бессрочно
**Раздел:** Собственный транспорт / Dashboard

Напоминания об истечении ОСАГО/КАСКО/техосмотра архивной машины продолжают показываться в виджете "истекающие документы" бесконечно.
**Файл/API:** `app/api/dashboard/route.ts:271-289`, `prisma/schema.prisma:402-415`
**Рекомендация:** При выборке фильтровать `DocumentExpiry` по актуальному статусу связанной машины (join через `entityId`, отдельным запросом, раз связь не через FK).

## Что уже работает правильно

- **`FuelRecord` (ручной журнал `/fuel`) действительно нигде не суммируется** — читается только на собственной странице и в двух проверках "сколько записей затронет удаление". Конвенция из CLAUDE.md подтверждена.
- **Реальная недоступность Wialon API (сеть/таймаут) не затирает данные** — при исключении `calculateVehicleTripTotals` оставляет уже сохранённые значения и не пишет в БД. Это отдельный, уже правильно обработанный случай — баг TMS-AUDIT-0021 касается именно "Wialon ответил успешно, но без данных", а не недоступности.
- Привязка `Vehicle.wialonUnitId` (`matchVehiclesWithWialon`) — не разрушающая, не перезаписывает уже установленную связь.
- Миграция геозон на TMS-native `CompanyZone` (Фаза 7 по памяти проекта) — рабочая, с защитой от ложного срабатывания при первом наблюдении.
- Обработка ошибок Wialon API в read-only роутах (`test-connection`, `fleet-snapshot`, `vehicle-live`) — устойчивая, различает "Wialon недоступен" от неожиданной ошибки, деградирует по отдельным машинам без падения всего запроса.
- Пагинация длинных интервалов сообщений Wialon (до 250k сообщений) — не усекает пробег на многонедельных рейсах.
- Нулевая привязка заявок к рейсу ("Ожидают привязки") — корректно отображается, не теряется из сумм.
- Отмена (`status='cancelled'`) заявки — последовательно исключается из дохода везде.
- Деление на 0 в коэффициентных хелперах (`costPerKm`, `profitPerKm`, `per100Km`) — везде защищено, не падает.
- Структурно невозможно задвоение `FleetExpense` с `Maintenance`/`ServiceRecord`/`PartPurchase` — разные модели без связи.
- Архивация машины (soft-only, hard-delete недостижим через приложение) — не ломает связанные записи (остаются на месте), риск hard-delete из документации кода — спящий, не активный.
