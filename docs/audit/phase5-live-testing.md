### 🔴 TMS-AUDIT-0041 — Бэкап вложений (документов заявок) не автоматизирован: один ручной прогон за всё время
**Раздел:** Резервное копирование
**Проблема:** Скрипт `scripts/attachments-backup-daily.ps1` существует и рабочий (лог показывает один успешный прогон `2026-08-01 17:42:54`, архив 69.8 МБ), но **в Планировщике задач Windows нет ни одной задачи для него** — `Get-ScheduledTask` показывает только `LevAV PostgreSQL Daily Backup`, `LevAV Wialon Mileage Sync`, `LevAV Company Base Check`. В отличие от БД (где есть `Install-LevAv-WialonSyncTask.ps1`-подобный инсталлятор), для вложений установочного скрипта не найдено вовсе.
**Как воспроизвести:** `Get-ScheduledTask | Where TaskName -like '*ttachment*'` — пусто. Лог `attachments_backup.log` — 1 запись за всё время, 8 дней назад.
**Последствие:** Все документы, приложенные к заявкам с 1 августа (счета, акты, сканы контрактов) — **не бэкапятся вообще**. При потере диска/повреждении `storage/uploads` восстановится только БД (со ссылками на файлы), сами файлы — нет.
**Файл:** `scripts/attachments-backup-daily.ps1`
**Рекомендация:** Создать `Install-LevAv-AttachmentsBackupTask.ps1` по образцу существующих инсталляторов Wialon-задач и зарегистрировать ежедневную задачу.

### 🔴 TMS-AUDIT-0042 — Копирование бэкапа БД на Google Drive простаивало 4 дня без единого уведомления
**Раздел:** Резервное копирование
**Проблема (живой инцидент, обнаружен и частично устранён в ходе аудита):** Лог `google_drive_backup.log` показывает, что с **2026-08-06 по 2026-08-09** копирование на `G:\Мой диск\LevAv_DB_Backups` не удавалось — диск `G:` не был смонтирован (`GoogleDriveFS` не поднялся к моменту ежедневной задачи 13:00), автоматическая логика remount (добавленная более ранним фиксом, упомянутым в CLAUDE.md, commit `8911a12`) честно пытается перезапустить Google Drive Desktop, но таймаут 45 секунд оказался недостаточным — сервис поднимался позже. Результат — `SKIP: Google Drive root not available` **4 раза подряд**, только в лог-файл, без какого-либо алерта пользователю (email/уведомление/что-либо видимое в UI системы).
**Локальный `pg_dump` при этом отрабатывал исправно все 4 дня** — оффлайн-копия на диске `C:` не прерывалась, под угрозой был только внешний (офсайт) экземпляр бэкапа.
**Обнаружено и устранено в рамках аудита:** на момент проверки `GoogleDriveFS` уже поднялся (стартовал в 13:29, уже после неудачной попытки 13:00 сегодняшнего дня) — недостающие 4 дневных бэкапа (06.08–09.08) скопированы на `G:` вручную командой в рамках этой сессии, разрыв закрыт.
**Файл/лог:** `scripts/copy-sql-backup-to-google-drive.ps1`, `C:\Users\user\LevAv_Postgres_Backups\logs\google_drive_backup.log`
**Рекомендация:** Увеличить таймаут ожидания remount (45с недостаточно), и главное — добавить видимое уведомление (хотя бы баннер в Dashboard, аналогично уже существующему "Finance Audit banner") при N подряд неудачных копированиях на Google Drive, а не только запись в файл лога, который никто не читает проактивно.

## 🟠 HIGH — новая находка живого тестирования

### TMS-AUDIT-0043 — Конкурентное редактирование одной заявки: последняя запись молча побеждает, изменения теряются без предупреждения
**Раздел:** Заявки / Конкурентность
**Проблема:** `PUT /api/trips/[id]` не использует оптимистическую блокировку (нет проверки версии/`updatedAt` от клиента перед записью) — прямое подтверждение раздела 17 ТЗ ("потеря изменений и конфликты").
**Как воспроизвели (реально, не гипотетически):** Две сессии (dispatcher на "ПК1", accountant на "ПК2") одновременно открывают одну и ту же тестовую заявку. Пользователь A меняет `routeTo`→"RaceA", `clientRate`→1111. Пользователь B (одновременно, независимо) меняет `routeTo`→"RaceB", `clientRate`→2222. Оба запроса вернули `HTTP 200` без единой ошибки. Итоговое состояние заявки — **полностью версия B**, правки A исчезли бесследно, ни один из пользователей не получил предупреждения о конфликте.
**Ожидаемый результат:** Либо блокировка второй записи с сообщением "заявка изменена другим пользователем, обновите страницу", либо явное слияние непересекающихся полей.
**Фактический результат:** Тихая потеря данных одного из двух одновременно работающих пользователей — ровно то, о чём предупреждает раздел 17 ТЗ применительно к работе с разных ПК.
**Файл/API:** `app/api/trips/[id]/route.ts` (PUT, весь хендлер — нет проверки `updatedAt`/версии)
**Рекомендация:** Добавить оптимистическую блокировку: клиент отправляет последний известный `updatedAt`, сервер сравнивает с текущим в БД и возвращает 409 при несовпадении.

## 🟢 Live-подтверждённые находки из предыдущих фаз

Прямыми API-запросами против боевой БД (с последующим откатом побочных эффектов) подтверждены вживую:

- **TMS-AUDIT-0013/0014** — dispatcher одним `PUT /api/trips/[id]` перевёл тестовую заявку из статуса "new" напрямую в "completed", без единой проверки перехода, без чек-листа долга/налогового кода. Подтверждено: `HTTP 200`, статус изменился.
- **TMS-AUDIT-0016** — после перевода заявки в "completed": (а) dispatcher успешно изменил `clientRate` на "закрытой" заявке (`HTTP 200`), (б) dispatcher успешно добавил платёж на "закрытую" заявку (`HTTP 201`) — обе операции прошли без единой проверки статуса.
- **TMS-AUDIT-0002/0003** — dispatcher (роль без доступа к критичным финансовым полям по документированной модели) успешно вызвал `PUT /api/exchange-rates` (сменил курс валют компании) и `POST /api/trips/revalue` (`{"currency":"USD","newRate":401}`), который **реально пересчитал 25 боевых заявок** без единого запроса подтверждения или предупреждения о масштабе воздействия — живое доказательство критичности находки, не гипотетическое. Инцидент полностью устранён (см. врезку в начале документа).
- **TMS-AUDIT-0019 (гонка нумерации счёт/акт)** — проверено вживую двумя параллельными вызовами `generate-docs` для двух заявок одного клиента: в этой конкретной попытке коллизии не произошло (СЧ-001/СЧ-002 — разные номера), что ожидаемо для узкого TOCTOU-окна гонки. Отсутствие блокировки в коде (`lib/doc-numbering.ts`) подтверждено статически в фазе 2 — риск остаётся, живой тест лишь не попал в окно гонки с первой попытки.
