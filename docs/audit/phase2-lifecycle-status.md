## Найденная модель статусов

`Trip.status` — свободная строка (не enum в БД): `new → in_progress → unloaded → awaiting_payment → sverka → completed`, плюс `archived`/`cancelled` (входимы/выходимы из любого состояния), плюс легаси-алиас `paid` = `completed`.

Гварды в `lib/trip-workflow-guards.ts`:
- `assertDirectWorkflowStatusChange` — проверяет соседство статусов (не более 1 шага) — используется только в `PATCH`.
- `assertCompletedWorkflowTransition` — проверяет `sverka→completed` — **нигде не вызывается**, кроме собственного теста.
- `assertReopenToAwaitingPaymentTransition` — **нигде не вызывается**, и даже если бы вызывалась — сама сломана: `completed`(idx5)→`awaiting_payment`(idx3) отличается на 2 шага, а гвард допускает максимум 1, то есть функция **всегда отклоняла бы** ровно ту переход, которую должна разрешать (это видно и из её же теста).
- `assertInitialTripWorkflowStatus` — работает корректно, используется в `POST /api/trips`.

Отдельный модуль `lib/trip-archive-rules.ts` (`validateTripArchiveTransition`) — реальный рабочий гвард (статус=completed + заполненный taxCode), используется в `POST /api/trips/[id]/archive`. Это единственный по-настоящему работающий backend-гвард во всей цепочке.

## 🔴 CRITICAL

### TMS-AUDIT-0013 — Реальная кнопка "Сохранить" пишет статус без какой-либо проверки перехода
**Раздел:** Заявки / Статусы
**Функция:** `PUT /api/trips/[id]` (основной путь сохранения формы заявки)
**Проблема:** `route.ts:179` пишет `body.status` напрямую в БД — без вызова `assertDirectWorkflowStatusChange`, без проверки долга/налогового кода, без проверки роли на поле `status`. Канбан-пилюли в `trip-form.tsx` (`:1032-1068`) — чисто клиентское состояние (`setStatus(key)`), реальное сохранение идёт через этот же PUT.
**Как воспроизвести:** Любая роль (включая dispatcher) → `PUT /api/trips/{id}` с телом, где `status: 'completed'`, на заявке в статусе `new`, с непогашенным долгом клиента/перевозчика и пустым `taxCode`. Запрос успешен, статус меняется, пропускаются `in_progress/unloaded/awaiting_payment/sverka`.
**Ожидаемый результат:** Сервер отклоняет недопустимый переход и/или требует выполненный чек-лист перед `completed`.
**Фактический результат:** Любой переход в любой статус проходит без проверок.
**Файл/API:** `app/api/trips/[id]/route.ts:179`
**Причина:** Гварды написаны, но подключены только к `PATCH`, которым реально никто не пользуется (см. TMS-AUDIT-0014).
**Рекомендация:** Вызывать `assertDirectWorkflowStatusChange` (и после исправления TMS-AUDIT-0014 — чек-лист для `completed`) внутри `PUT`, а не только `PATCH`.

### TMS-AUDIT-0014 — Задокументированный гейт "Сверка → чек-лист долг/налоговый код → Завершён" не работает ни в одном реально используемом пути
**Раздел:** Заявки / Статусы / Финансы
**Функция:** Переход в статус "Завершён"
**Проблема:** Единственный код с реальной проверкой чек-листа — `POST /api/trips/[id]/close` (`close/route.ts:10-65`, 3 условия: долг клиента, долг перевозчика для экспедиции, `taxCode`) — **не вызывается никогда** ни из одного места фронтенда (grep по всему `app/` не находит вызовов, кроме `PUT /close` для reopen). Функция `handleCompleteTrip` в `trip-form.tsx:685-719`, которая могла бы быть точкой входа, сама нигде не подключена к JSX (мёртвый код), и даже если бы была подключена — вызывает `PATCH`, а `PATCH` проверяет только соседство статусов (`assertDirectWorkflowStatusChange`), не чек-лист.
**Как воспроизвести:** Провести заявку через реальный UI из "Сверка" в "Завершён" (через сохранение формы, TMS-AUDIT-0013) с незакрытым долгом и без налогового кода.
**Ожидаемый результат:** Блокировка перехода, требование по CLAUDE.md/бизнес-процессу.
**Фактический результат:** Переход проходит беспрепятственно — задокументированное правило не действует нигде, где реально работают пользователи.
**Файл/API:** `app/api/trips/[id]/close/route.ts` (мёртвый), `app/api/trips/[id]/route.ts` (реальный путь без проверки), `trip-form.tsx:685-719` (мёртвый код)
**Причина:** Похоже, реализация чек-листа осталась от более раннего варианта UI (отдельная кнопка "Завершить"), которую заменили инлайн-канбаном в форме, но серверную проверку не перенесли.
**Рекомендация:** Либо подключить существующую логику `close/route.ts` к реальному пути сохранения (`PUT`), либо продублировать её проверку прямо в `PUT`-хендлере перед записью `status: 'completed'`.

### TMS-AUDIT-0015 — Reopen устанавливает не тот статус, без проверки роли, вторым несогласованным способом выхода из архива
**Раздел:** Заявки / Статусы / Права доступа
**Функция:** `PUT /api/trips/[id]/close` (reopen)
**Проблема:** Расширяет находку Фазы 1 (TMS-AUDIT-0004/0008). Комментарий в коде (`:148`) утверждает "вернуть в 'unloaded'", неиспользуемый гвард целится в `'awaiting_payment'`, а фактический код (`:165`) выставляет `'sverka'`. Также принимает `archived` как исходное состояние (`:159`) и возвращает сразу в `sverka`, минуя корректный `un-archive` эндпоинт в `archive/route.ts` (который правильно восстанавливает в `completed`, `:57`) — то есть существует два разных, несогласованных способа выйти из архива, один из которых без проверки роли откатывает на 2 шага назад в workflow.
**Файл/API:** `app/api/trips/[id]/close/route.ts:148-173` vs `app/api/trips/[id]/archive/route.ts:57`
**Рекомендация:** Оставить один путь выхода из `archived` (через `archive` route), удалить/исправить дублирующую ветку reopen в `close/route.ts`, добавить проверку роли.

### TMS-AUDIT-0016 — Ничего не замораживает финансовые данные завершённой/архивной заявки на уровне API
**Раздел:** Заявки / Финансы / Статусы
**Проблема:** `PUT /api/trips/[id]` не проверяет статус вообще — ставки, маршрут, расходы, `taxCode` можно переписать на заявке в статусе `completed` или `archived` прямым API-запросом. `POST/DELETE /api/payments` также не проверяют `trip.status` — платежи можно создавать/удалять на архивной заявке любой ролью из `TRIP_PAYMENT_JOURNAL_ROLES` (включая dispatcher). Единственная "заморозка" — клиентская (`trip-form.tsx:118`, `formLocked = isArchived || isCancelled`, и заметьте — `completed` туда не входит даже на UI-уровне), тривиально обходится прямым запросом к API.
**Как воспроизвести:** Завершить/заархивировать заявку → `PUT /api/trips/{id}` с изменённой `clientRate`/`carrierRate` → изменения применяются, `profitAmd` пересчитывается задним числом на "закрытой" сделке.
**Файл/API:** `app/api/trips/[id]/route.ts` (PUT, весь), `app/api/payments/route.ts:72-157`
**Рекомендация:** Добавить проверку статуса на уровне API: `completed`/`archived` → запрет изменения финансовых полей и создания/удаления платежей без явного reopen (который сам должен требовать роли — см. TMS-AUDIT-0015).

## 🟠 HIGH

### TMS-AUDIT-0017 — `Trip.driverId` и `VehicleTrip.driverId` — независимые поля без синхронизации, расхождение путает аналитику по водителям
**Раздел:** Собственный транспорт / Аналитика
**Проблема:** У Trip есть собственный `driverId`, у привязанного `VehicleTrip` — свой независимый `driverId`. `resolveVehicleTripLink` (`lib/vehicle-trips/attach-service.ts:44-74`) проверяет совпадение `vehicleId`, но **никогда** не проверяет `driverId` (grep по `lib/vehicle-trips/` не находит ни одного сравнения). `app/api/driver-analytics/route.ts` при этом относит выручку/прибыль по `Trip.driverId` (line 39), а расход топлива — по `VehicleTrip.driverId` (line 23-36, есть даже явный комментарий об этом на line 47). Если поля расходятся — выручка и расход топлива одной и той же заявки попадают на карточки разных водителей.
**Как воспроизвести:** Привязать заявку с `driverId=A` к рейсу (`VehicleTrip`) с `driverId=B` → открыть аналитику по водителям A и B за период → выручка/прибыль будет у A, топливо — у B.
**Файл/API:** `lib/vehicle-trips/attach-service.ts:44-74`, `app/api/driver-analytics/route.ts:23-47`
**Рекомендация:** Добавить сравнение `driverId` в `resolveVehicleTripLink` (минимум — предупреждение, лучше — блокировка при расхождении).

## 🟡 MEDIUM

### TMS-AUDIT-0018 — Удаление заявки не проверяет вложения и не чистит файлы на диске
**Раздел:** Заявки / Удаление данных
**Проблема:** `DELETE /api/trips/[id]` (`route.ts:417-452`) блокирует удаление только по `expenses`/`payments`/`vehicleTripId`, но не по `TripAttachment`. Заявка без расходов/платежей/привязки рейса, но с загруженными документами — удаляется; DB-каскад (`onDelete: Cascade`) чистит строки `TripAttachment`, но `deleteStoredFile` (используется корректно в точечном удалении вложения, `attachments/route.ts:83`) здесь не вызывается вовсе — физические файлы остаются на диске навсегда, ничем более не связанные. Также удаление не пишет запись в `TripHistory` перед `prisma.trip.delete` — кто и когда удалил заявку, не фиксируется нигде.
**Файл/API:** `app/api/trips/[id]/route.ts:417-452`
**Рекомендация:** Перед удалением заявки — enumerate вложения и вызвать `deleteStoredFile` для каждого; либо блокировать удаление при наличии вложений (симметрично expenses/payments).

### TMS-AUDIT-0019 — Гонка при генерации номеров счёта/акта может выдать два разных рейса с одинаковым номером
**Раздел:** Документы / Конкурентность
**Проблема:** `getNextDocNumberPair` (`lib/doc-numbering.ts:62-109`) читает `client.lastInvoiceNum/lastActNum` и пишет инкремент внутри `prisma.$transaction`, но без `SELECT ... FOR UPDATE`/явного уровня изоляции `Serializable`. При стандартном Postgres `READ COMMITTED` два параллельных вызова `POST /api/trips/[id]/generate-docs` для одного клиента (два диспетчера почти одновременно генерируют документы по двум разным заявкам одного клиента) могут прочитать одинаковый `lastInvoiceNum` до коммита друг друга — оба рейса получат **один и тот же** номер счёта/акта. На `Trip.invoiceDocNumber`/`actDocNumber` нет вообще никакого unique-constraint в БД, поэтому дубликат не будет пойман даже постфактум.
**Файл/API:** `lib/doc-numbering.ts:62-109`, вызывается из `app/api/trips/[id]/generate-docs/route.ts:38-47`
**Рекомендация:** `SELECT ... FOR UPDATE` на строку клиента внутри транзакции, либо перевести транзакцию в `Serializable` с retry.

## 🔵 LOW

### TMS-AUDIT-0020 — `distance`/`cargoValue`/`cargoWeight` = 0 превращается в `null` на клиенте
**Раздел:** Заявки / Форма
**Проблема:** `trip-form.tsx:926` и аналогичные строки используют `value ? Number(value) : null` — легитимный `0` (falsy) превращается в `null`. Маловероятно критично для км/веса груза, но технически некорректно.
**Рекомендация:** Использовать явную проверку `value === '' || value == null` вместо truthy-проверки.

## Что уже работает правильно

- **Field-drop для Trip — не найден.** Все поля формы (`clientId`, ставки, валюты, курсы, даты, `expenses[]`, назначение машины/водителя, номера счетов и т.д.) корректно доходят до Prisma-записи и в POST, и в PUT.
- `validateTripPayload` (`lib/trip-payload-validation.ts`) дублирует серверную валидацию обязательных полей — закрывает обход клиентской валидации через прямой API-запрос.
- Роль-гейтинг денормализованных платёжных полей (`clientPaidAmount*`/`carrierPaidAmount*`) — применяется единообразно в POST/PUT/PATCH.
- `Payment` create/delete — корректно пересчитывает `clientPaidAmount(Amd)`/статус внутри транзакции с advisory lock (защита от гонки при одновременном добавлении платежей).
- `VehicleTrip` ↔ `Trip` — `onDelete: SetNull` на уровне БД, удаление рейса не оставляет висячий `vehicleTripId`. `DELETE /api/vehicle-trips` корректно блокируется при наличии связанных Trip/FleetExpense/FuelRecord.
- `resolveVehicleTripLink` — корректно проверяет совпадение `vehicleId` при привязке (но не `driverId`, см. TMS-AUDIT-0017).
- Редактирование карточки клиента/перевозчика **не** ретроактивно меняет уже сохранённые `clientRateAmd`/`carrierRateAmd`/`profitAmd` старых заявок — суммы считаются и хранятся на момент создания/правки самой заявки. Подтверждено соответствие требованию CLAUDE.md.
- Жёсткое удаление клиента корректно блокируется при наличии заявок; удаление перевозчика — намеренно только архивация (в коде есть явный комментарий почему хард-делит убрали).
- `Trip.tripNumber` — уникален на уровне БД, с retry-циклом при создании (race-safe).
- `POST /api/trips/[id]/archive` — единственный по-настоящему работающий гейт статуса (`completed` + `taxCode` обязателен).
